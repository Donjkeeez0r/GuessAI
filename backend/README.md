# GuessAI — бэкенд

Реалтайм-викторина для Telegram Mini App: паки вопросов, генерация через Gemini,
озвучка через Google TTS, игровые комнаты на socket.io.

Стек: NestJS 11, Prisma 7 + PostgreSQL, Redis (ioredis), socket.io 4.

Контракт API и WebSocket — в `../CONTRACT.md`. Это источник правды: любое
расхождение кода с ним считается багом кода.

---

## Структура

| Модуль | Ответственность |
|---|---|
| `auth` | проверка Telegram `initData`, выпуск JWT |
| `users` | профиль, история игр, глобальный лидерборд |
| `pack` | CRUD паков и AI-генерация |
| `ai` | Gemini, TTS-ссылки, стоп-лист тем и модерация контента |
| `room` | хранилище комнат в Redis, реестр публичных лобби |
| `game` | игровой цикл: `game.service.ts` — логика, `game.gateway.ts` — транспорт |

Разделение состояния комнаты:

- `IRoomState` (`src/room/room.types.ts`) — полное состояние с вопросами и
  правильными ответами, живёт **только в Redis**;
- `PublicRoomState` — то, что уходит клиентам. Единственный сериализатор —
  `toPublicRoomState()`; все исходящие эмиты комнаты обязаны идти через него.

Аналогично для REST: `toPublicPack()` в `src/pack/pack.mapper.ts` срезает
`correctOption` и `explanation` — правильные ответы не покидают сервер до `ROUND_END`.
Единственное исключение — автор собственного **не-ИИ** пака: гейт
`isPackAnswersOwner()` отдаёт ему ответы, чтобы редактор не требовал
переотмечать правильные варианты. ИИ-пак исключён намеренно: его «автор»
ответов не писал, и отдать их значило бы дать сыграть с подсказками.

### Совместимость комнат при выкатке

Комнаты живут в Redis до `ROOM_TTL_SECONDS` и переживают перезапуск с новой
версией кода. Запись, сериализованная **до** появления поля, вернулась бы с
`undefined` — а, например, `Math.min(packSize, undefined)` даёт `NaN` и ломает
счётчик вопросов. Поэтому недостающие поля добираются в `normalizeRoom()` —
единственной точке чтения комнаты (`src/room/room.service.ts`). Добавляя поле
в `IRoomState`, добавляйте его и туда.

## Модель данных

Схема — `prisma/schema.prisma`, миграции — `prisma/migrations/`.

| Модель | Смысл | Заметки о связях |
|---|---|---|
| `User` | игрок из Telegram | `telegramId` уникален; `rating` — текущий ELO |
| `Pack` | пак вопросов | `author` → `User` с `onDelete: SetNull`: удаление автора не уносит пак |
| `Question` | вопрос пака | `pack` → `Pack` с `onDelete: Cascade` |
| `GameSession` | сыгранная партия | ссылается на `Pack` **без** каскада: пак с историей не удалить |
| `GamePlayer` | результат игрока в партии | каскад и от `User`, и от `GameSession` |

Партия «в процессе» в базе не лежит вовсе — только в Redis. В Postgres она
попадает один раз, в момент `GAME_OVER`, вместе с пересчётом рейтинга.

Счётчики `totalGames` и `wins` в `GET /users/me`, как и глобальный лидерборд,
считаются **только по партиям, где был хотя бы один соперник**. Лидерборд —
единственное место в проекте с сырым SQL: корреляцию «в сессии был кто-то ещё»
для всех игроков разом Prisma во вложенном `some` не выражает, а `ROW_NUMBER()`
даёт абсолютный ранг одним проходом. Тай-брейк `ORDER BY rating DESC, id`
обязателен: без него ранг при равных рейтингах прыгает между запросами.

## Запуск в Docker

```bash
# из корня репозитория
cp .env.example .env   # и заполнить значения
docker compose up -d db redis backend
```

Контейнер бэкенда на старте сам применяет `prisma migrate deploy`, затем
запускает `node dist/src/main`. Поднять весь стек разом — `docker compose up -d`
из корня: тогда фронт встанет на `:8080` и сам будет проксировать `/api` и
`/socket.io` на бэкенд.

Две мелочи, ради которых в `docker-compose.yaml` заданы `name: guessai` и явные
`image: guessai-backend` / `image: guessai-frontend`: без них Compose берёт имя
проекта из имени каталога и может перезаписать образы постороннего проекта,
если каталог называется так же.

### HTTPS

Telegram Mini App открывается только по HTTPS. `docker compose` отдаёт чистый
HTTP, поэтому для реального запуска нужен reverse-proxy с сертификатом
(nginx/Caddy + Let's Encrypt) или туннель — `cloudflared`, `ngrok`. Полученный
HTTPS-адрес прописывается в BotFather как URL Mini App — и только туда: адрес
бэкенда во фронт не вшивается, потому что nginx контейнера фронта сам проксирует
`/api` и `/socket.io` на бэкенд. Поэтому туннель нужен один — на порт фронтенда
(`scripts/tunnel.sh` поднимает его и печатает адрес), а пересобирать фронт при
смене адреса не нужно.

## Игровой цикл

Раундами управляет **сервер**, клиент никогда не двигает вопросы.

```
START_GAME → ROUND_START → приём SUBMIT_ANSWER → ROUND_END
           → пауза ROUND_REVEAL_MS → следующий ROUND_START или GAME_OVER
```

Раунд закрывается по таймеру длительности раунда либо досрочно, как только
ответили все подключённые игроки. `ROUND_START.endsAt` — epoch-миллисекунды по
часам сервера, клиент синхронизирует свой таймер по ним.

**Порядок событий на старте обязателен:** сначала `ROUND_START`, затем
`ROOM_UPDATED` со `status: 'PLAYING'`. Обратный порядок на мгновение показал бы
лобби и увёл бы игрока с игрового экрана, а без второго события у клиента
статус комнаты остался бы `LOBBY` — и разрыв связи не переключил бы экран на
переподключение.

Пока комната в `LOBBY`, хост меняет её параметры, и оба события сбрасывают
готовность до исходной (готов только хост) — игроки соглашались на прежние
правила:

| Событие | Что меняет |
|---|---|
| `CHANGE_PACK` | пак комнаты; лимит вопросов переживает смену, но упирается в размер нового пака |
| `CHANGE_SETTINGS` | число вопросов (5/10/15/`null` = весь пак) и длительность раунда (10/15/20/30 с) |

Значения вне этих списков отвергаются **молча**: приходят они только из
самодельного клиента, отдельного кода ошибки на них не заведено.

**Если лимит меньше пака, вопросы берутся случайным подмножеством.** Вопросы
грузятся `orderBy: id asc`, поэтому «первые пять» означали бы один и тот же
набор в каждой партии на этом паке — реванш шёл бы по уже сыгранным вопросам.
Внутри выбранного набора порядок остаётся паковым.

Отдельные ветки того же цикла:

- `SOLO_GAME` — тренировка: приватная комната на одного и сразу первый раунд,
  лобби не показывается. В историю попадает, в счётчики игр и побед — нет.
- `REMATCH` — из `FINISHED` обратно в `LOBBY`: очки и серии обнуляются,
  отключившиеся выбывают, публичная комната снова открывается для `QUICK_MATCH`.
- `LEAVE_ROOM` во время партии приравнен к обрыву связи: игрок остаётся в
  комнате с замороженными очками и доигрывает заочно. Иначе кнопка выхода была
  бы способом слить партию без потери рейтинга.

Очки:

```
base   = 100 + floor(100 * оставшееся время / длительность раунда)
mult   = [1, 1.25, 1.5, 2][min(серия до этого ответа, 3)]
gained = верный ответ ? floor(base * mult) : 0
```

`answeredAt` фиксируется на сервере в момент прихода события — время от клиента
не принимается.

**Серия (`IPlayer.streak`).** Множитель берётся по серии **до** текущего ответа:
первый правильный ответ идёт по ×1, а наградой за него становится множитель
следующего. Серию обнуляет и неправильный ответ, и **пропуск раунда** — иначе
промолчать было бы выгоднее, чем рискнуть и промахнуться, поэтому обнуление
не ответивших живёт в `endRound`, а не только в `submitAnswer`. Серии
обнуляются у всех при `START_GAME` и при реванше.

По `GAME_OVER` в одной транзакции пишутся `GameSession` и `GamePlayer` и
пересчитывается рейтинг по многопользовательскому ELO (`K = 32`, нижняя
граница 100). Игра с одним участником рейтинг не меняет, но в историю попадает.

### Ограничение: таймеры в памяти процесса

Таймеры раундов живут в `Map<roomId, NodeJS.Timeout>` внутри `GameService`
и заводятся на `room.roundDurationMs` — ту же длительность, что ушла клиентам
в `ROUND_START`, иначе раунд закрылся бы не тогда, когда показывает таймер.
При одном инстансе сервера этого достаточно, но отсюда следуют два ограничения:

1. **Рестарт процесса теряет идущие игры.** Состояние комнаты в Redis
   переживёт перезапуск, а таймер — нет: раунд не закроется сам.
2. **Горизонтальное масштабирование не работает.** Таймер заведён на том
   инстансе, куда пришёл `START_GAME`; события других игроков могут попасть на
   соседний инстанс, который об этом таймере не знает.

Когда понадобится больше одного инстанса или устойчивость к рестарту, таймеры
переезжают на BullMQ с отложенными задачами: `ROUND_END` и переход к следующему
раунду становятся job'ами в общей очереди на Redis, а `GameService` — их
обработчиком. Сейчас BullMQ намеренно не подключён.

Дополнительно: для сокет-адаптера при масштабировании понадобится
`@socket.io/redis-adapter`, иначе broadcast не дойдёт до игроков на других
инстансах.
